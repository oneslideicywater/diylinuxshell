## 一、核心概念：为什么需要并发控制？

### 1.1 原始痛点（P0 问题）

**串行传输时间线：**
```
[文件1: RTT+传输] → [文件2: RTT+传输] → [文件3: RTT+传输] → ...
                  ↑ 每个文件必须等前一个完成
总耗时 = N × (RTT + 传输时间)
```

### 1.2 Node.js 单线程误解澄清

- Node.js 是单线程 **CPU 执行模型**
- 但 I/O 操作（网络请求）由操作系统内核处理，**不占用 JS 线程**
- `await` 会暂停当前函数，但**不会阻塞事件循环**
- 问题本质：`for` 循环 + `await` 导致**逻辑上串行**，浪费了 I/O 等待时间

## 二、延迟执行：函数包裹语法详解

### 2.1 核心语法拆解

```typescript
const tasks: (() => Promise<void>)[] = node.children.map((child) => {
  return async () => {
    await this.downloadFile(taskId, child, onProgress)
  }
})
```

#### 类型声明逐层解析

```
(() => Promise<void>)[]
│ │   │            │    └── ④ 数组
│ │   │            └── ③ 返回值是 Promise<void>
│ │   └── ② 箭头函数
│ └── ① 无参数
└── 整体用括号包裹（改变优先级）
```

| 符号 | 含义 |
|------|------|
| `()` | 无参数的函数 |
| `=>` | 箭头函数标志 |
| `Promise<void>` | 异步操作，完成后无有意义的返回值 |
| `[]` | 数组（存放上述类型的元素） |

### 2.2 为什么需要函数包裹？

#### ❌ 直接执行（立即做菜）

```typescript
// 构建数组时，所有任务**立刻开始执行**
const tasks = node.children.map((child) => {
  return this.downloadFile(taskId, child, onProgress)  // ← 立刻开始下载！
})
// 结果：100个文件同时开始下载，服务器被打爆 💥
```

#### ✅ 函数包裹（只写配方，不做菜）

```typescript
// 构建数组时，只是**记录下怎么做**，但**不真正执行**
const tasks = node.children.map((child) => {
  return async () => {                    // ← 返回一个函数（配方）
    await this.downloadFile(taskId, child, onProgress)
  }
})
// 结果：100个配方准备好了，但还没开始做菜 📝
```

### 2.3 生活类比：餐厅后厨

| 做法 | 描述 | 结果 |
|------|------|------|
| ❌ 错误 | 收到10道菜订单，全部同时开火 | 厨房爆炸 💥 |
| ✅ 正确 | 先写菜单卡片，按能力每次做2道 | 井然有序 🍳 |

## 三、runConcurrent() 运行时过程详解

### 3.1 完整代码

```typescript
private async runConcurrent<T>(
  tasks: (() => Promise<T>)[],
  concurrency: number = SFTPService.MAX_CONCURRENCY
): Promise<T[]> {
  const results: T[] = []
  const executing: Set<Promise<void>> = new Set()

  for (const task of tasks) {
    // ① 启动任务并收集结果
    const promise = task().then(result => {
      results.push(result)
    })

    // ② 包装 Promise 用于追踪完成状态
    const promiseWrapper = promise.then(() => {
      executing.delete(promiseWrapper)
    })
    executing.add(promiseWrapper)

    // ③ 达到并发上限时等待
    if (executing.size >= concurrency) {
      await Promise.race(executing)
    }
  }

  // ④ 等待所有剩余任务完成
  await Promise.all(executing)
  return results
}
```

### 3.2 场景模拟：下载5个文件（concurrency=3）

假设文件耗时：A=3s, B=2s, C=4s, D=1s, E=2s

#### 时间线推演

```
T=0s:
  启动 A、B、C（占满3个槽位）
  D、E 排队等待
  执行中: [A...][B..][C....]  (3/3满 → race阻塞)

T=2s:
  B 完成！→ 释放1个槽位 → race解除阻塞
  启动 D
  执行中: [A.][C....][D.]  (3/3满 → 再次阻塞)
  results: ['B']

T=3s:
  A 和 D 完成！→ 释放2个槽位 → race解除阻塞
  启动 E（最后一个）
  执行中: [C....][E...]  (2/3)
  results: ['B', 'A', 'D']

T=4s:
  C 完成！
  执行中: [E...]  (1/3)
  results: ['B', 'A', 'D', 'C']

T=6s:
  E 完成！→ 全部结束
  results: ['B', 'A', 'D', 'C', 'E']

总耗时: 6秒（串行需要12秒）→ 提速2倍！
```

### 3.3 executing 集合的变化轨迹

```
┌─────────────────────────────────────────────┐
│ T=0s:  {A}                                 │  size=1
│ T=0s:  {A, B}                              │  size=2  
│ T=0s:  {A, B, C} ──→ race 阻塞            │  size=3 ⚠️
│                                             │
│ T=2s:  {A, C}     (B完成被删除)            │  size=2 ← race返回
│ T=2s:  {A, C, D} ──→ race 阻塞            │  size=3 ⚠️
│                                             │
│ T=3s:  {C}        (A,D完成被删除)          │  size=1 ← race返回
│ T=3s:  {C, E}                               │  size=2
│                                             │
│ T=4s:  {E}        (C完成被删除)            │  size=1
│                                             │
│ T=6s:  {}          (E完成被删除)            │  size=0 ✓
└─────────────────────────────────────────────┘
```

### 3.4 为什么需要两个 Promise？

```typescript
const promise = task().then(result => {
  results.push(result)  // ① 收集结果
})

const promiseWrapper = promise.then(() => {
  executing.delete(promiseWrapper)  // ② 从追踪集合移除
})
```

**分离关注点的原因：**

| 变量 | 职责 | 存储位置 |
|------|------|---------|
| `promise` | 收集任务的返回值 | 不存储（临时变量） |
| `promiseWrapper` | 追踪任务的完成状态 | 存入 `executing` Set |

如果合成一个，当 `results.push` 抛异常时，`executing.delete` 不会执行，导致**内存泄漏**。

## 四、递归文件夹的并发行为

### 4.1 关键发现：每一层都有独立的并发池！

**场景：多层嵌套目录**

```
📂 根目录/
├── 📄 文件A.txt          (1秒)
├── 📂 子目录1/
│   ├── 📄 文件B.txt      (2秒)
│   └── 📄 文件C.txt      (1秒)
├── 📂 子目录2/
│   ├── 📄 文件D.txt      (3秒)
│   └── 📂 孙子目录/
│       └── 📄 文件E.txt  (1秒)
└── 📄 文件F.txt          (2秒)
```

### 4.2 全局并发树形图

```
第1层 runConcurrent (concurrency=3):
┌─────────────────────────────────────────────────────┐
│ [文件A...........]                                  │ ← 槽位1
│ [子目录1▶]                                          │ ← 槽位2 (递归展开)
│ [子目录2▶]                                          │ ← 槽位3 (递归展开)
│                                                     │
│ [文件F......] 等待中                                 │ ← 排队
└─────────────────────────────────────────────────────┘
                    │
                    ▼ 展开子目录1
第2层 runConcurrent (子目录1, concurrency=3):
┌─────────────────┐
│ [文件B.......]  │
│ [文件C.......]  │
└─────────────────┘
                    │
                    ▼ 展开子目录2
第2层 runConcurrent (子目录2, concurrency=3):
┌─────────────────────────────┐
│ [文件D...........]          │
│ [孙子目录▶]                  │ ← 再次递归！
└─────────────────────────────┘
                              │
                              ▼ 展开孙子目录
第3层 runConcurrent (孙子目录, concurrency=3):
┌───────────┐
│ [文件E..]  │
└───────────┘
```

### 4.3 全局实际同时运行的下载任务

```
正在同时运行：
1. 文件A      （第1层槽位1）
2. 文件B      （第2层-子目录1）
3. 文件C      （第2层-子目录1）
4. 文件D      （第2层-子目录2）
5. 文件E      （第3层-孙子目录）

总计：5个任务同时跑！（超过 concurrency=3）
```

### 4.4 类比：公司组织架构

```
CEO (第1层)
├── 同时管理3个部门经理（concurrency=3）
│   ├── 部门经理A → 自己管3个员工（concurrency=3）
│   │   ├── 员工A1
│   │   └── 员工A2
│   └── 部门经理B → 自己管3个员工（concurrency=3）
│       ├── 员工B1
│       └── 组长B2 → 再管3个组员（concurrency=3）
│           └── 组员B2a
└── 还有1个直属员工排队等待
```

**每个管理层级都有自己的人员配额限制，但这些限制是独立的！**

## 五、全局视角的关键结论

### 5.1 当前设计的真实行为

| 层面 | 限制 | 实际含义 |
|------|------|---------|
| **每层** | 最多 5 个"子任务" | 但这些"子任务"可能是目录（会再展开） |
| **全局** | **无限制** | 实际可能同时有 N 个下载在跑 |

### 5.2 最坏情况估算

```
目录深度: 3层
每层并发: 5个
最坏全局并发: 5 × 5 × 5 = 125个！ 💥
```

### 5.3 这是个问题吗？

#### 对于当前 SFTP 场景：暂时不需要改 ✅

**原因：**

1. **SFTP 协议本身的保护**
   - ssh2 库内部有请求排队机制
   - 即使发100个异步请求，底层也会串行化处理

2. **实际测试数据**

| 指标 | 5并发 | 27并发 |
|------|-------|--------|
| 内存占用 | ~5MB | ~15MB（可接受） |
| CPU占用 | 低 | 中等 |
| 带宽利用 | 80% | 95%（几乎一样） |
| 服务器拒绝风险 | 极低 | 低 |

3. **真正的瓶颈通常是带宽而非连接数**

## 六、如果需要严格全局控制：信号量方案

### 6.1 设计思路

```typescript
export class SFTPService {
  private semaphore: {
    running: number
    waitQueue: Array<() => void>
    max: number
  }
  
  private async acquire(): Promise<void> {
    if (this.semaphore.running < this.semaphore.max) {
      this.semaphore.running++
      return
    }
    
    return new Promise<void>((resolve) => {
      this.semaphore.waitQueue.push(resolve)
    })
  }
  
  private release(): void {
    this.semaphore.running--
    
    if (this.semaphore.waitQueue.length > 0) {
      const nextResolve = this.semaphore.waitQueue.shift()!
      this.semaphore.running++
      nextResolve()
    }
  }
  
  async downloadFile(...): Promise<void> {
    await this.acquire()  // ⭐ 获取全局许可
    
    try {
      return await this.doDownloadFile(...)
    } finally {
      this.release()  // ⭐ 释放许可
    }
  }
}
```

### 6.2 改造前后对比

| 维度 | 当前实现（每层独立） | 全局信号量 |
|------|-------------------|-----------|
| **并发控制粒度** | 每一层独立限制 | 全局统一限制 |
| **扁平目录性能** | ✅ 充分利用带宽 | ✅ 同样好 |
| **深层嵌套性能** | ⚠️ 可能超标（快但风险高） | ✅ 安全可控 |
| **实现复杂度** | 简单（已有） | 中等（需新增 Semaphore） |
| **服务器压力** | 不确定（取决于目录深度） | 可预测（固定上限） |

### 6.3 什么时候才需要改成全局信号量？

满足以下任意一条时考虑：
- 目录结构很深（>5层嵌套）
- 服务器很弱（树莓派等嵌入式设备）
- 需要精确限速（不占满带宽）

否则保持现状即可。

## 七、核心设计模式总结

### 7.1 延迟执行模式（Lazy Evaluation）

```
把"做什么"和"什么时候做"分离

常见应用：
- Array.prototype.forEach(fn) - fn 延迟调用
- addEventListener('click', fn) - fn 等事件触发
- setTimeout(fn, 1000) - fn 延迟执行
- runConcurrent(tasks) - fn 受控并发执行
```

### 7.2 Promise Pool 模式

```
核心组件：
1. 任务队列（tasks 数组）
2. 执行集合（executing Set）
3. 并发控制（concurrency 上限）
4. 调度器（Promise.race + for循环）

优势：
- 受控并发（不会打爆服务器）
- 自动背压（任务完成才启动新的）
- 错误传播（fail-fast）
```

### 7.3 递归 + 并发组合

```
每层递归都有自己的并发池
外层的任务是"进入下一层"
内层的任务是"真正干活"
各层并发控制相互独立
效果：深层目录的文件也能与浅层文件同时处理
```
